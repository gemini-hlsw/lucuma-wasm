# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Inside `nix develop` (or with direnv, automatically) two devshell commands wrap everything:

    check         # cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test
    build-wasm    # wasm-pack build --release --target web -> pkg/

Run `check` before finishing any change; CI runs exactly those three steps plus the wasm build.

Single test: `cargo test <test_fn_name>` (e.g. `cargo test ellipse_matches_jts_100_gon`). All
tests live in the `mod tests` block at the bottom of `src/lib.rs` and run on the host target, not
wasm.

Release: tag `vX.Y.Z` matching the `version` in `Cargo.toml`; the Release workflow fails the build
if they disagree, then `npm publish`es `pkg/`.

## Architecture

One crate, one file (`src/lib.rs`), one purpose: give lucuma-core's Scala.js `ShapeExpression`
interpreter a fast polygon kernel. It is deliberately *not* a JTS port; it exposes only the
operations `ShapeExpression` needs.

**Handle arena.** Geometries are never passed across the wasm boundary. They live in two
`thread_local!` `RefCell`s: `ARENA` (a `Vec<Option<MultiPolygon<f64>>>`) and `FREE` (recycled
indices). Every constructor and every operation returns a `u32` handle via `put`; every read goes
through `with`, which panics on a freed or unknown handle (surfaces in JS as an exception). `free`
is idempotent and pushes the slot onto `FREE`, so handle values are reused; `live()` exists purely
so the Scala side can assert no leaks in its tests. Consequence: **every function that returns a
handle allocates a new arena slot** — the caller owns it and must `free` it. Adding a new
operation means following that same put/with contract, or the facade's leak tests break.

**MultiPolygon-only.** Every geometry is a `MultiPolygon`, even a rectangle or an empty shape.
That keeps `geo`'s `BooleanOps` total (no type dispatch, no mixed-dimension results) at the cost of
not representing lines or points.

**JTS-compatible point placement.** `ellipse_new` and `arc_new` reproduce JTS
`GeometricShapeFactory` vertex placement exactly (start angle 0, `npts` around the ring for the
ellipse; centre → `npts` arc points → centre for the arc, with an out-of-range `extent` meaning a
full circle). Areas therefore differ from the true conic by a known factor, and the tests assert
those closed-form JTS values (`50 * sin(2π/n)` for a 100-gon unit circle). If you change vertex
generation you break bit-comparability with lucuma-jts, which is the point of the crate. Values
are compared with a relative tolerance helper, not `==`.

**Units are the caller's.** Coordinates are plain `f64`; lucuma-core passes microarcseconds with
`x = -p`, `y = q`. Nothing here knows about angles or scales.

`bbox` returns four NaNs for an empty geometry rather than an option, so the JS side can test one
value. Keep that convention.

## Conventions

`--target web` output must load both in the browser and in Node, so nothing may depend on
`fetch(file:)`. Node callers pass the bytes explicitly:
`init({ module_or_path: fs.readFileSync(pathToWasm) })`.

`pkg/` is generated by wasm-pack; never edit it by hand.
